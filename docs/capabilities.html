The ledger

A limitation documented beats a capability faked.

Every claim this project could make, classified — with the mechanism behind it and how it fails. Verified against Claude Code 2.1.119 on Windows 11, against the hooks reference, and against real payloads captured from live sessions.

supported

Things it genuinely does.

ClaimMechanismFailure mode
Session lifecycle SessionStart / SessionEnd, one hook entry per matcher so the reason is known from the URL. A hard kill fires nothing; the session holds its last real status until a 10-minute TTL prunes it. It never invents a “disconnected”.
Tool activity with real targets
payload captured		 PreToolUse / PostToolUse with tool_name + tool_input. An unknown tool degrades to Using <Tool>; unreadable input degrades to Thinking…. Never a guessed filename.
Permission detection with the real command
payload captured		 PermissionRequest (primary) with Notification[permission_prompt] as a de-duplicated backstop. If neither fires, the bar shows WORKING and simply doesn't know. It will not infer a prompt from silence.
Telling a real prompt from an auto-approved one The prompt must outlive a 700 ms grace window before buttons or a toast appear. A genuine prompt surfaces 700 ms late — inside the one-second target. A pathologically slow auto-approval would flash briefly.
Completion with a summary
payload captured		 Stop, using last_assistant_message. Missing field falls back to Done.
Typed API errors StopFailure — the matcher is the error class (rate_limit, overloaded, billing_error…). An unlabelled class renders as Failed: <class> rather than a generic error.
Interrupt vs failure
payload captured		 PostToolUseFailure.is_interrupt — true when you pressed Esc. —
File-change tracking PostToolUse on Edit/Write/MultiEdit/NotebookEdit. A file written by a shell redirect inside Bash is invisible — only tool-level writes count.
Concurrent sessions
verified with 3 live		 session_id keys everything; cwd matches against the bridge's workspace folders. —
Closing the overlay can't affect your session
measured		 Hook connection failure, timeout and non-2xx are all non-blocking by design. Tool calls ran in 39 ms and 67 ms with every hook pointed at a dead server.

partially supported

Things it half does.

ClaimWhat worksWhat doesn't
“Waiting for input” vs idle Notification matchers idle_prompt, agent_needs_input and elicitation_dialog map to WAITING_FOR_INPUT. These matchers are documented but were never observed firing during capture, so the mapping comes from the reference rather than a recorded payload. Treat it as best-effort.
Test / build results A failed Bash call shows as a failed activity item with the real error text. Nothing knows that npm test is the test suite, or that exit 0 means green. Inferring “tests passed” is a guess, so it isn't made.
Elapsed time Accurate from UserPromptSubmit, which is when the turn genuinely starts. A session first observed mid-turn starts its clock at the first event seen, under-reporting. Never backdated.
Reading the transcript file transcript_path is on every payload, so the file is locatable. Deliberately unused. It lags the live conversation and its format is not a stable public contract. last_assistant_message is the supported route.
macOS / Linux Portable code — no Win32 APIs, no shelling out, POSIX chmod 0600 on the token. Untested anywhere but Windows 11. Always-on-top levels, notifications and the vscode:// fallback are the likely rough edges.

not possible

Things it will never do.

ClaimWhy
Know the moment a permission is granted Permission grants are silent — no hook fires. The order is PreToolUse → PermissionRequest → PostToolUse with nothing between; only denials by the auto-mode classifier get an event. So approving in VS Code leaves the earliest hard evidence at the tool finishing. Mitigated by acknowledgement on focus or on [Open VS Code] — never by claiming approval.
Watch Codex, Gemini, or any agent other than Claude Code Not supported. Tested against Codex: it does not work. The reason is transport, not events — worth stating precisely, because “they have no hooks” would be wrong. Codex CLI has hooks (SessionStart, PreToolUse, PostToolUse, PermissionRequest, Stop…), and so does Gemini CLI, with similar payload fields. But both run local commands only, delivering JSON on stdin — Codex's docs state plainly that only type: "command" handlers run. Claude Code is currently the only one that can POST a hook event to an HTTP URL, and this app's receiver is HTTP, so nothing from the others arrives. Bridging one is feasible: a relay script that reads stdin and POSTs to the receiver, plus a per-agent config installer and payload verification against real captures. A genuine piece of work, not a small adapter.
Read Claude Code's in-memory state No API exposes another extension's internals. The VS Code Extension API cannot see inside Claude Code at all. This is the assumption that sinks naive versions of this project.
Read terminal scrollback There is no supported VS Code API to read a terminal's buffer. Shell integration events don't give you the text.
Know what Claude is “thinking” No hook fires during model inference. A long gap between tool calls is genuinely opaque — which is why silence dims the bar but never changes its status, and why the honest label is just Thinking….
Raise the VS Code window from the extension VS Code exposes no API for an extension to bring its own OS window to the front. Raising is done by opening an already-open file via vscode://file/ — which is why a real file path matters, and why a folder is never used.
Detect a hard-killed session SessionEnd doesn't fire on kill -9. The session just stops emitting, which is indistinguishable from a long think. Resolved by a TTL, not a guess.
Approve permissions (v1, by choice) Mechanically supported — PermissionRequest accepts a decision in the response body — but deliberately not built. It means holding the HTTP response open until you click, blocking that tool call against a 600-second default timeout, and an overlay that can approve tool calls deserves its own threat model. [ok] acknowledges only.

If you upgrade Claude Code

Re-verify these four.

  • SessionStart supports type: "http". On 2.1.119, WorktreeCreate is the only event restricted to command/mcp_tool. Earlier builds restricted more.
  • A 2xx body is meaningful. Text gets injected into Claude's context; JSON is parsed as a decision. The ingest handler returns 204 with no body, always — a stray log line would silently pollute your conversations.
  • The default HTTP hook timeout is 600 seconds. Every installed hook carries an explicit short timeout (5 s, and 1 s for SessionEnd, which shares a ~1.5 s budget).
  • Hook failure is non-blocking. This is the property that makes the whole design acceptable, and it is tested.
